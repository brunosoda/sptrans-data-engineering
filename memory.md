# SPTrans Bus Tracking — Agent Memory

**Purpose:** Preserve a traceable history of bus-position observations for route 516N, direction 1, and estimate when a selected vehicle reaches the route's origin and destination areas. This file records the current design and decisions discussed on 15–17 October 2026. DuckDB is the only database used in this project; downstream transformations described below are not yet implemented.

**Scope note:** This was assembled from the recent conversation context available in this session, the SPTrans README in the accessible Library, and the public GitHub files checked on 17 October 2026. The interface did not expose a searchable archive of every ChatGPT conversation in the account, so it is not a verified exhaustive review of all chats.

## 1. Runtime flow

1. `track_516n.py` authenticates with the SPTrans Olho Vivo API and identifies the internal line code for `516N-10`, direction `1`.
2. The script polls the line-position endpoint in a loop. `POLL_INTERVAL_SECONDS = 5` means it sleeps for five seconds between loop iterations under normal conditions; the actual time between requests is approximately the request/processing duration plus that sleep.
   - **Connection error retry policy:** If an HTTP request raises a `requests.exceptions.ConnectionError`, the loop waits `RETRY_INTERVAL_SECONDS = 1` second before retrying instead of waiting the full 5 seconds. If connection is restored on the subsequent request, it automatically reverts to the default `POLL_INTERVAL_SECONDS = 5`. This prevents a gap of 10s or more between successful observations during transient network hiccups, mitigating the risk of the vehicle passing the destination endpoint undetected.
3. While waiting for a vehicle to enter the origin radius, the script logs API requests and checks returned vehicles, but does not insert their positions into `raw_vehicle_positions`.
4. After selecting a vehicle near the origin, the script follows that vehicle. If it appears in a response, its position fields are inserted into `raw_vehicle_positions`, then the position is checked for freshness and used for trip tracking.
5. The intended result is to record the observation associated with the origin and destination proximity checks and calculate elapsed travel time. The current configuration uses a 250 m proximity radius and a predefined trip distance of 2,300 m for the average-speed calculation.

This is **near-real-time polling**, not a push-based streaming service. Five seconds is a practical sampling choice for observing a moving vehicle; it trades temporal detail against API usage and local processing. Confirm the API's current usage terms and limits before treating this interval as a production setting.

## 2. Layers and why the raw layer exists

**Source / ingestion:** SPTrans returns current vehicle-position snapshots. Python requests those snapshots and adds request-level collection metadata.

**Raw layer:** retain the source fields (`cl`, `p`, `a`, `ta`, `py`, `px`) alongside metadata (`request_uuid`, `fetched_at`). Preserve repeated observations even if the coordinates are unchanged: the same vehicle at the same coordinates on different polls can be a valid observation at a different time. Raw data supports auditing, debugging, historical tracking, and later reprocessing without having to invent the original source values.

**Possible downstream layers (not currently implemented):**

- **Staging:** standardize types and column names, parse source timestamps, and apply basic validation while keeping one row per raw observation.
- **Intermediate:** implement reusable business logic such as fresh-position filtering and route-event detection.
- **Marts / analytical outputs:** expose metrics such as origin detection time, destination detection time, elapsed trip duration, and estimated average speed.

The project currently uses the local DuckDB database file `sptrans.duckdb`. DuckDB is the only database used in this project. Staging, intermediate, and mart layers below are conceptual downstream layers, not existing implemented models.

## 3. Table A — `raw.api_request_logs`

This table records one outcome for each API request attempt, including failed attempts. The fields below describe the DuckDB tables. The repository file `create_tables.sql` was used as a reference for field names and types, but it should not be labeled as PostgreSQL-only without checking compatibility with the installed DuckDB version.

| Column | DuckDB type / intended type | Meaning |
|---|---|---|
| `request_uuid` | `UUID PRIMARY KEY` | Unique correlation ID generated by Python for each API request. |
| `request_started_at` | `TIMESTAMPTZ` | When the request started. |
| `request_finished_at` | `TIMESTAMPTZ` | When the response or request failure finished being handled. |
| `request_duration_ms` | `BIGINT` | Request duration in milliseconds, measured with a monotonic performance timer. |
| `status` | `VARCHAR` | Outcome label, currently including values such as `success`, `timeout`, `http_error`, or `request_error`. |
| `error_type` | `VARCHAR` | Exception class name when the request fails; otherwise null. |
| `http_status_code` | `INTEGER` | HTTP response status code when available. |
| `loaded_at` | `TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP` | Database insertion time, distinct from request and source-observation times. |

The request log is operational metadata: it helps answer whether a request succeeded, how long it took, and when/why failures happened. A failed request can have a log row even when it produced no usable positions.

## 4. Table B — `raw.raw_vehicle_positions`

This table stores the raw position fields for the selected vehicle during the tracking phase, plus request and collection metadata. The fields below describe the DuckDB table. Confirm exact types against the actual table definition in `sptrans.duckdb` if it differs from the DDL file.

| Column | DuckDB type / intended type | Meaning |
|---|---|---|
| `request_uuid` | `UUID NOT NULL` | The request that returned this position. One request UUID may occur on multiple position rows if multiple returned vehicles are stored. |
| `fetched_at` | `TIMESTAMPTZ` | When the API response was fetched/finished by the collector; it is the collection time, not the SPTrans source timestamp. |
| `cl` | `BIGINT` | SPTrans internal line code. |
| `p` | `VARCHAR` | Vehicle prefix/identifier. |
| `a` | `BOOLEAN` | Whether the vehicle is marked as accessible in the API response. |
| `ta` | `VARCHAR` | Original SPTrans timestamp associated with the position. The script parses this as an ISO-8601 UTC timestamp for freshness and ordering, but the raw column preserves it as text. |
| `py` | `DOUBLE` | Latitude. |
| `px` | `DOUBLE` | Longitude. |
| `loaded_at` | `TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP` | Database insertion time, if this column is present in the active DuckDB table. |

The raw position table is intentionally historical/append-oriented: it is not a “current position per vehicle” table. The current raw-position table is append-oriented and has no known primary or unique key that would prevent repeated inserts.

## 5. Relationship between the tables

The logical relationship is **one request log row to zero, one, or many position rows**:

- `raw.api_request_logs.request_uuid` is the parent key.
- `raw.raw_vehicle_positions.request_uuid` identifies the request that produced the position.
- `track_516n.py` generates a UUID once inside each `get_line_vehicles()` call and returns that same UUID with the result. The request log and the position rows from that response should share it; do not generate a separate request UUID for each vehicle row.

Example SQL join in DuckDB:

```sql
SELECT
    p.*,
    r.request_started_at,
    r.request_finished_at,
    r.request_duration_ms,
    r.status,
    r.http_status_code
FROM raw.raw_vehicle_positions AS p
JOIN raw.api_request_logs AS r
    ON r.request_uuid = p.request_uuid;
```

The DDL declares the request-log primary key but does **not** declare a foreign-key constraint on the position table. The relationship above is logical and queryable by UUID; a foreign key could be considered if the ingestion process guarantees the corresponding log row is successfully persisted before or with each position batch. In the public tracker version checked, the script only inserts the selected vehicle during the tracking phase, so usually no more than one position row is inserted per request; the model can support multiple rows if ingestion later stores all vehicles from a response. Verify the local working copy because it may be newer than GitHub.

## 6. Why each API request gets a new UUID

A UUID identifies a **request attempt**, not a bus or a position. Each new poll is a new observation opportunity and therefore gets a new request UUID. Multiple rows from one API response share that request UUID, enabling lineage from a position row back to the HTTP outcome and timing metadata. `request_uuid` is not intended to deduplicate unchanged coordinates.

## 7. Timestamp meanings — do not treat them as interchangeable

- **`request_started_at`:** when the HTTP call starts.
- **`request_finished_at`:** when the call/response handling ends; useful alongside `request_duration_ms` for operational monitoring.
- **`fetched_at`:** the collection time attached to position rows after the request completes. It tells when this pipeline fetched the snapshot.
- **`ta`:** the source timestamp supplied with the vehicle position by SPTrans. It can differ from `fetched_at` if the API's position was captured earlier or its data is stale.
- **`loaded_at`:** the database's insertion time. It tells when the row reached the database, not when SPTrans observed the vehicle.

For tracking, `ta` is used by the current script to reject positions older than `MAX_POSITION_AGE_SECONDS` (180 seconds) and to ignore repeated or out-of-order observation timestamps when updating the tracking state. `fetched_at` remains useful for auditing collection cadence and API delays.

**Implementation caveat:** `prepare_api_logs_duckdb.py` currently normalizes `request_started_at` and `request_finished_at` to Python `datetime.time`, which discards the date and timezone before inserting them into DuckDB. This means those two log fields represent time-of-day only, not a full timestamp, and cannot reliably distinguish requests across dates. If cross-day chronology matters, preserve full datetimes and time-zone information in DuckDB.

## 8. Idempotency decision

Idempotency is **not currently enforced on `raw_vehicle_positions`**, and that is not automatically a design flaw. The purpose of this table is to retain a sequence of observations; identical coordinates returned on separate polls can be legitimate historical data. Removing rows only because `px` and `py` are unchanged would lose observation history and may weaken analysis of when a bus entered an endpoint's proximity radius.

The current script creates a new request UUID for each poll and inserts a row with `INSERT`; it does not use an idempotency key, a unique constraint, or an upsert for raw positions. Consequently:

- Separate polls returning the same position are stored as separate observations, by design.
- If the **same logical response/row is accidentally replayed** into the table, the current schema does not stop a duplicate insert.
- `request_uuid` alone cannot deduplicate across replays if a replay creates a new UUID.

Do not create a coordinate-only “deduplicated” table solely to claim idempotency. If replay-safe ingestion becomes a real requirement, define what counts as the same logical observation first and implement a stable observation key or ingestion-batch strategy. A separate table containing only coordinate changes is an optional business model, not an existing table; add it only if change events are useful for the analysis. It must retain the timestamp of each detected change, and event detection should account for out-of-order source timestamps.
